# Geo 函数性能优化项

## 1. 执行层：Batch / 对象复用（ROI 最高的工程项）

当前瓶颈：逐行 `from_encoded` → `new GeoShape` → 算完扔，无 batch。

### 可做的优化

**Batch decode**：一块内同一 VARCHAR blob 只解析一次结构头，或按字典/重复值短路

**Const 右侧重用**：`ST_Contains(region, ST_Point(116.4, 39.9))` 里右侧几何只构造一次（`st_distance` 已有 const/vector 三分支思路，可推广到关系函数）

**对象池 / 线程本地缓存**：避免每行 `unique_ptr` 分配

**轻量路径**：部分简单函数（`ST_X`/`ST_Y`/`ST_GeometryType`）可走更轻的路径，不必整棵 S2 树还原

> 这类不碰存储格式，改 `functions_geo` 就能见效。

---

## 2. 建模侧：拆经纬度 / 预计算列（用户立刻能用）

不必等内核：

```sql
-- 点用 DOUBLE 存，查询走 ST_Distance_Sphere，避免每行 ST_Point+encode+decode
lng DOUBLE, lat DOUBLE

-- 需要 ST_Contains 时再 ST_Point(lng, lat)

-- 固定区域可写进列，而不是每行 ST_GeomFromText(...)
region VARCHAR(...)   -- 导入时就算好 blob
```

或加生成列 / 物化视图：

```sql
s2_cell BIGINT  -- 由 lng/lat 算出 → 用 ZoneMap/Bloom 粗筛（类索引，不建 R-tree）
-- 预存 bbox_min_lng/max_lng/...，WHERE 先做矩形裁剪再 ST_Contains
```

---

## 3. FE 常量折叠（中等收益，局部场景）

只帮"一侧全是常量"的查询，例如固定多边形 + 逐行点：

- 折掉 `ST_GeomFromText('POLYGON...')` → 计划期一个常量 blob
- 省掉每行 WKT 解析
- 整句折成 TRUE 意义不大；**构造函数折叠更值当**

难点：二进制 VARCHAR Literal 与现有 `shouldSkipFold(st_*)`。

---

## 4. 专用列类型 ColumnGeo（中长期）

仍可不叫"索引"：

- 解码状态留在列里，扫描时不只吐不透明 blob
- ZoneMap 可挂 bbox（min/max lat/lng）做存储层粗过滤（谓词下推的弱形式）
- 比完整 R-tree/原生 GEOMETRY 协议栈轻一档，但比纯执行优化重

---

## 5. 算法与路径选择

- **能走球面距离就用 `ST_Distance_Sphere(lng,lat,...)`**，别强制 `ST_Point + ST_Distance`（少两次编解码）
- 大面/多环先 bbox 近似，精算放后
- 热点多边形可预转 S2 covering（cell 列表），用整数 `IN`/`BETWEEN` 粗筛——这是 S2 路线，仍不算传统空间索引树

---

## 6. 系统层（通用但有效）

- **投影裁剪**：不 `SELECT *`，少读大 VARCHAR region
- Pipeline 并行度 / 分区裁剪（按业务分区：城市、hash(geohash)）
- 列压缩与短 blob：点很小；超大多边形拉高 decode 成本，可简化几何或分块

---

## 优先级排布

| 手段 | 谁做 | 主要省什么 | 相对投入 |
|------|------|-----------|---------|
| 经纬度拆列 + 少用构造函数 | 用户/SQL | encode/decode、WKT | 低 |
| bbox / S2Cell 辅助列 | 用户或生成列 | 扫描行数（弱过滤） | 低～中 |
| BE batch + const 复用 + 对象池 | 内核 | 每行 CPU | 中 |
| 常量构造折叠 | FE | 每行 WKT 解析 | 中 |
| ColumnGeo + bbox ZoneMap | 内核 | 解码 + 粗过滤 | 高 |
| 完整空间索引 | 内核 | 大幅减行数 | 很高 |

### 结论

除了索引，最稳的是"执行路径减负"+"建模拆列/预计算"；真正贴近索引收益但更轻的是 **S2 CellId / bbox 辅助列 + ZoneMap**。完整 R-tree 在 OLAP 里仍是最后一档。
